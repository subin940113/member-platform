# 성능 및 부하 테스트 (k6)

## 1. 목적

회원가입은 아래 두 단계를 거쳐 처리합니다.

1. `POST /api/v1/members/admission`
2. `POST /api/v1/members`

입장 단계에서는 Redis 기반 유입 제어로 유입량을 제한하고, 회원가입 단계에서는 DB `UNIQUE` 제약과 `Idempotency-Key`로 최종 정합성을 보장합니다.

성능 테스트의 목적은 다음과 같습니다.

- 회원가입 전체 흐름의 처리량과 응답 시간 확인
- 부하 증가 시 어느 지점부터 병목이 발생하는지 확인
- 대량 회원가입 유입 시 입장 단계가 초과 요청을 적절히 제어하는지 확인
- 동시 요청 상황에서도 중복 처리 방지 정책이 유지되는지 확인


## 2. 테스트 환경

- Java 21 / Spring Boot 3.3.5
- 단일 애플리케이션 인스턴스
- PostgreSQL, Redis
- Docker Compose 기반 로컬 환경
- 부하 도구: k6

> 측정값은 로컬 장비 성능과 실행 시점의 자원 상태에 따라 달라질 수 있습니다.


## 3. 테스트 시나리오

### 3.1 회원가입 전체 흐름

대상 스크립트: `perf/k6/register-flow.js`

일정한 부하에서 입장 토큰 발급부터 회원가입 완료까지 전체 흐름을 확인합니다.

확인 항목
- 입장 단계 응답 시간
- 회원가입 단계 응답 시간
- end-to-end 응답 시간
- 전체 흐름 성공률


### 3.2 점진 부하 증가

대상 스크립트: `perf/k6/register-ramp.js`

요청량을 점진적으로 높이면서 입장 단계의 차단 동작과 회원가입 단계의 지연 변화를 함께 확인합니다.

확인 항목
- 입장 성공 수
- 입장 거절 수 (`429`)
- 회원가입 성공 수 (`201`)
- end-to-end 응답 시간
- 부하 증가에 따른 지연 변화


### 3.3 입장 API 급증 부하

대상 스크립트: `perf/k6/admission-spike.js`

입장 API에만 큰 유입을 주고, 초과 요청이 앞단에서 빠르게 제한되는지 확인합니다.

확인 항목
- 입장 성공 수
- 입장 거절 수 (`429`)
- 입장 단계 응답 시간
- 오류율


### 3.4 중복 요청 충돌

대상 스크립트: `perf/k6/idempotency-conflict.js`

동일한 `Idempotency-Key`를 반복 요청하여, 같은 요청이 동시에 중복 처리되지 않는지 확인합니다.

확인 항목
- 최초 성공 건수
- `409 MEMBER_REQUEST_IN_PROGRESS` 발생 건수
- 회원가입 단계 응답 시간
- 중복 처리 방지 여부


## 4. 테스트 결과

### 4.1 회원가입 전체 흐름

일정한 부하로 30초 동안 전체 회원가입 흐름을 실행했습니다.

| 항목 | 값 |
|---|---|
| 총 수행 횟수 | 601 |
| 입장 단계 p95 | 3.57 ms |
| 회원가입 단계 p95 | 85.75 ms |
| end-to-end p95 | 89 ms |
| 전체 흐름 성공률 | 100% |
| HTTP 실패율 | 0% |

- 일반적인 부하에서는 입장 단계의 비용이 매우 작습니다.
- 전체 응답 시간은 대부분 회원가입 처리 구간에서 결정됩니다.
- 회원가입 전체 흐름은 안정적으로 처리되었습니다.


### 4.2 점진 부하 증가

부하를 단계적으로 높이면서 회원가입 전체 흐름을 확인했습니다.

| 항목 | 값 |
|---|---|
| 총 수행 횟수 | 5,330 |
| 입장 성공 수 | 3,969 |
| 입장 거절 수 (`429`) | 1,361 |
| 회원가입 성공 수 (`201`) | 3,969 |
| 입장 단계 p95 | 98.66 ms |
| 회원가입 단계 p95 | 1,460.23 ms |
| end-to-end p95 | 1,489.55 ms |
| HTTP 실패율 | 0% |
| 입장 성공 요청 대비 가입 성공 비율 | 100% |

- 부하가 올라가면서 회원가입 단계의 응답 시간이 먼저 크게 증가했습니다.
- 입장 단계는 초과 요청을 `429`로 제한하면서, 회원가입 단계까지 전달되는 요청 수를 제어했습니다.
- 현재 로컬 단일 인스턴스 기준으로는 병목이 입장 단계보다 회원가입 단계에 더 가깝게 나타났습니다.
- 특히 DB write가 포함된 회원가입 처리 구간이 전체 지연에 더 큰 영향을 주는 것을 확인했습니다.


### 4.3 입장 API 급증 부하

입장 API만 분리해서 큰 유입을 넣고 차단 동작을 확인했습니다.

| 항목 | 값 |
|---|---|
| 총 요청 수 | 24,499 |
| 입장 성공 수 | 100 |
| 입장 거절 수 (`429`) | 24,399 |
| 입장 허용 비율 | 0.40% |
| 입장 단계 p95 | 53.38 ms |
| HTTP 실패율 | 0% |


- 초과 요청은 대부분 입장 단계에서 빠르게 `429`로 정리되었습니다.
- 입장 API만 놓고 보면, 과도한 유입에서도 응답 시간이 크게 흔들리지 않았습니다.
- 큰 유입이 들어오더라도 회원가입 처리 구간으로 모두 넘기지 않고 앞단에서 차단하는 구조가 정상적으로 동작했습니다.


### 4.4 중복 요청 충돌

동일한 `Idempotency-Key`를 반복 요청하면서 중복 처리 방지 정책을 확인했습니다.

| 항목 | 값 |
|---|---|
| 총 수행 횟수 | 1,088 |
| 회원가입 성공 수 (`201`) | 10 |
| 회원가입 충돌 수 (`409`) | 1,078 |
| 입장 단계 p95 | 4.51 ms |
| 회원가입 단계 p95 | 100.71 ms |
| HTTP 실패율 | 0% |


- 동일한 `Idempotency-Key` 그룹에서는 최초 1건만 처리되고, 이후 요청은 `409`로 정리되었습니다.
- 중복 요청이 동시에 여러 번 처리되는 현상은 관찰되지 않았습니다.
- 대량 요청 상황에서도 중복 처리 방지 정책은 일관되게 동작했습니다.


## 5. 결론

회원가입 전체 흐름, 부하 증가 구간, 입장 단계 차단 동작, 중복 처리 방지 정책을 각각 분리해서 확인했습니다.

- 일반적인 부하에서는 회원가입 전체 흐름이 안정적으로 처리됩니다.
- 부하가 증가하면 입장 단계가 초과 요청을 먼저 제한하고, 실제 병목은 회원가입 단계에서 더 뚜렷하게 나타납니다.
- 대량 유입 상황에서도 입장 단계는 빠르게 `429`를 반환하며 시스템을 보호합니다.
- 동일 요청은 `Idempotency-Key`를 통해 중복 처리되지 않습니다.

정리하면, 현재 구조는 모든 요청을 그대로 뒤로 넘기는 방식이 아니라 입장 단계에서 유입량을 조절하고, 회원가입 처리 구간에서는 중복 요청을 제한하는 방식으로 동작합니다. 로컬 단일 인스턴스 기준에서도 이런 설계가 의도대로 동작하는 것을 확인했습니다.
